# Deploying Alturia (free tier)

Four services, all free, chosen specifically so the whole thing survives
months of inactivity between now and sustentación without losing data —
see the comparison below before picking anything else.

| Service | Role | Why this one |
| --- | --- | --- |
| [Neon](https://neon.tech) | PostgreSQL + pgvector | Free tier suspends compute after 5 min idle but **never deletes data** — just wakes up on the next query. Render's own free Postgres deletes the database after 30 days + a 14-day grace period. |
| [Render](https://render.com) | NestJS API | Free web services sleep after 15 min idle (30-60s cold start) but are **never deleted**. Fine to leave dormant for months — just ping it a few minutes before presenting. |
| [Vercel](https://vercel.com) | Dashboard + widget | Static hosting, no inactivity expiry at all. |
| [OpenRouter](https://openrouter.ai) | Production LLM | `qwen/qwen3.6-plus:free` — free model, no card required. |

No paid tier anywhere in this path. `EMBEDDING_PROVIDER` is deliberately left
as `ollama` even in production (see `render.yaml`'s comment) — nothing in the
current code path actually calls it, so there's no reason to sign up for
OpenAI (which may ask for billing info) just to satisfy an unused check.

I can't create accounts for you (that's a "you sign in" step by design, not
something to hand off), so this is a guided walkthrough — I've verified the
build/boot side locally (see below), but the actual platform accounts and
their quirks are untested until you click through them. If something errors
partway, paste it back and I'll help debug.

**What I already verified locally**, so these parts aren't guesswork:
- Built `apps/api` and ran the compiled output (`node dist/src/main.js`) with
  the real `.env` file removed and only inline env vars — confirms the app
  boots correctly from plain `process.env`, the way Render will run it (no
  `.env` file exists in production).
- Confirmed the actual compiled entry path is `dist/src/main.js`, not
  `dist/main.js` — `render.yaml`'s `startCommand` is already set correctly.

## 1. Neon (database)

1. Sign up at [neon.tech](https://neon.tech) (GitHub login is fastest).
2. Create a project — any name (e.g. `alturia`), region close to you.
3. From the project dashboard, copy the **connection string** (the one with
   `?sslmode=require` at the end). Keep it somewhere for step 2.
4. pgvector is a standard extension Neon supports — no extra setup needed,
   our migration already runs `CREATE EXTENSION IF NOT EXISTS "vector"`.

## 2. Render (API)

1. Sign up at [render.com](https://render.com) with GitHub, and grant it
   access to the `Alturia` repo.
2. **New +** → **Blueprint** → pick the `Alturia` repo. Render reads
   `render.yaml` from the repo root and proposes the `alturia-api` service.
3. Before confirming, you'll be prompted for the env vars marked
   `sync: false` in `render.yaml`:
   - `DATABASE_URL` → the Neon connection string from step 1
   - `OPENROUTER_API_KEY` → from [openrouter.ai/keys](https://openrouter.ai/keys)
     (sign up free, no card required for the `:free` model)
   - `SEED_ADMIN_PASSWORD` → pick a real password for the admin dashboard login
     (don't leave the `changeme123` dev default in production)
   - `JWT_SECRET` is auto-generated by Render (`generateValue: true`) — nothing to enter
4. Deploy. First build takes a few minutes (pnpm install + two builds). Watch
   the logs — if it fails, the error is almost always a missing/misnamed env
   var at this point, since the code itself is already verified to boot.
5. Once live, copy the service URL (`https://alturia-api-xxxx.onrender.com`)
   — you'll need it in step 3.

### Apply the schema + seed (run once, from your machine)

```bash
# Point at Neon instead of local Postgres, just for this one command:
DATABASE_URL="<neon connection string>" pnpm --filter api exec prisma migrate deploy

# Same for the seed — use a real SEED_ADMIN_PASSWORD, matching what you set in Render:
DATABASE_URL="<neon connection string>" SEED_ADMIN_PASSWORD="<your real password>" \
  pnpm --filter api run seed
```

## 3. Vercel (dashboard + widget)

Two separate Vercel projects from the same repo — one per app.

**Dashboard:**
1. [vercel.com](https://vercel.com) → sign up with GitHub → **Add New →
   Project** → import `Alturia`.
2. **Root Directory**: click Edit, select `apps/dashboard`.
3. Framework preset: Vite (auto-detected). Leave build/output commands default.
4. In **Build & Development Settings**, enable **"Include files outside the
   Root Directory in the Build Step"** — required so the build can see
   `packages/shared` (pnpm workspace dependency).
5. **Environment Variables**: add `VITE_API_BASE_URL` = your Render URL from
   step 2 (e.g. `https://alturia-api-xxxx.onrender.com`).
6. Deploy.

**Widget:** repeat the same project-import flow, but:
- Root Directory: `apps/widget`
- Same "include files outside root" toggle
- Environment Variable: `VITE_WIDGET_API_BASE_URL` = the same Render URL
- After it deploys, your embeddable script URL is
  `https://<your-widget-project>.vercel.app/widget.js`

## 4. Wire it into asisaltura.co (or wherever you demo it)

```html
<script src="https://<your-widget-project>.vercel.app/widget.js" defer></script>
```

Same one-line embed we tested locally against the portfolio — nothing about
the snippet changes, only the URL.

**Your portfolio is already live** at
[portafolio-web-nine-lyart.vercel.app](https://portafolio-web-nine-lyart.vercel.app/)
(not just local) — once the widget and API are deployed, update
`app/layout.tsx`'s `<Script src="...">` in the portfolio repo to point at the
real Vercel widget URL instead of `http://localhost:5174/widget.js`, then
push. That gives you a fully public, live demo (not just your laptop) to
show the professor, with zero risk to the portfolio's own infra — still just
that one script tag.

## Before the actual demo day

Both Render (API) and Neon (DB) go dormant after inactivity — harmless, but
add a cold-start delay on the very first request. A few minutes before
presenting:

```bash
curl https://alturia-api-xxxx.onrender.com/
```

This wakes both up (the health check hits the DB-backed app, which wakes
Neon too) so the actual demo doesn't stall on a 30-60s cold start in front
of the professor.
